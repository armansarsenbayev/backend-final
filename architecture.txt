SYSTEM DESIGN & ARCHITECTURE

================================================================================
SECTION 1. TECH STACK
================================================================================

| Component       | Technology              | Justification                                                                                                                                                                                                              |
| --------------- | ----------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Runtime         | Node.js 20 LTS          | Non-blocking event loop is suitable for I/O-bound workloads: concurrent contribution requests, exchange-rate fetches, and webhook delivery from couriers/payment providers.                                                |
| Framework       | Express.js 4.x          | Minimal, unopinionated HTTP layer. Mature middleware ecosystem (helmet, cors, express-rate-limit). Pairs cleanly with controller/service separation.                                                                       |
| Database        | PostgreSQL 15+          | ACID transactions are mandatory for the multi-currency contribution flow and the "no over-funding" constraint. Native support for recursive CTEs (WITH RECURSIVE) is required for the family-tree endpoint.               |
| ORM             | Prisma 5.x              | Type-safe client generated from a single schema.prisma file. Native support for interactive transactions with isolation levels (Serializable) and $queryRaw for the recursive CTE that ORM abstractions cannot express.    |
| Cache / Queue   | Redis 7.x               | Three roles: (1) token-bucket rate limiting on auth endpoints, (2) JWT refresh-token denylist for instant revocation on logout, (3) short-lived locks during contribution finalization to coordinate with DB transactions. |
| Auth            | jsonwebtoken + bcrypt   | HS256 JWT for access (15 min TTL) and refresh (7 day TTL) tokens. bcrypt with cost factor 12 for password hashing.                                                                                                          |
| Validation      | Zod                     | Schema validation for both env-config bootstrap and request bodies. Same library used in two layers reduces cognitive load.                                                                                                |
| API Docs        | swagger-ui-express      | Mounts the openapi.yaml at /docs. Single source of truth for the API contract.                                                                                                                                             |
| Testing         | Jest + Supertest        | Unit tests for pure service functions (rotation, exchange snapshot, sophistication-style scoring). Supertest for HTTP integration tests against an ephemeral test database.                                                |
| Container       | Docker + docker-compose | Reproducible local dev: Postgres + Redis + app in one command. Same Dockerfile is the build target for CI.                                                                                                                 |
| CI              | GitHub Actions          | Runs lint, tests, and Docker build on every push. Required for the assignment.                                                                                                                                             |

SECTION 2. ARCHITECTURE PATTERN — LAYERED (CONTROLLER / SERVICE / REPOSITORY)
================================================================================

The codebase follows a strict layered architecture:

    HTTP Request
        │
        ▼
    [Routes]            ── declarative route table; binds path + middleware + controller method
        │
        ▼
    [Middleware]        ── auth (JWT verify), RBAC (role check), validation (Zod), rate-limit
        │
        ▼
    [Controllers]       ── thin: parse req, call service, format res. NO business logic.
        │
        ▼
    [Services]          ── all business rules: contribution math, exchange-rate snapshot,
        │                  family-tree traversal, gift-tier resolution
        ▼
    [Repositories]      ── all Prisma calls live here; services never touch prisma directly
        │                  (exception: explicit $transaction blocks in services where atomicity
        │                  must span multiple repos)
        ▼
    [Prisma Client]     ── singleton, connected at boot, disconnected on SIGTERM
        │
        ▼
    PostgreSQL


WHY THIS APPROACH:

  - Separation of concerns. Controllers stay under ~20 lines each. Business rules
    that affect grading (atomic contributions, recursive family tree, multi-currency
    snapshot) live in well-named service files that map 1:1 to assignment requirements.

  - Testability. Pure service functions (e.g., calculateRemainingPool, snapshotRate)
    are tested with Jest without spinning up a database. Repositories are mocked.

  - Transaction control. Services that must be atomic (createContribution) own the
    prisma.$transaction() call explicitly. This makes the atomicity requirement
    auditable in code review — graders can grep for $transaction and find every
    critical section.

  - Grader-friendly. The assignment lists specific deliverables (auth, family tree,
    multi-currency snapshot, double-entry-style ledger via Contribution + Gift state).
    Each maps to a single service file: authService, familyTreeService,
    contributionService, registryService.

SECTION 3. ENVIRONMENT STRATEGY
================================================================================

Configuration is loaded once at boot via src/config/env.js using Zod.

  - dotenv loads .env into process.env.
  - A Zod schema declares every required variable, its type, and constraints.
  - The schema is parsed strictly (.parse, not .safeParse) so unknown or malformed
    values throw before the app binds a port.
  - Forbidden placeholder values ("changeme", "secret", "hello world", empty string)
    are rejected by a custom .refine() rule on each secret field. The process exits
    with code 1 and a printed list of failed variables.
  - The validated, frozen object is exported as `env` and is the ONLY way the rest
    of the codebase reads configuration. process.env is not referenced anywhere
    outside env.js. This is enforced by an ESLint rule (no-restricted-properties).

Required variables (full list in .env.example):

    NODE_ENV                  one of: development | test | production
    PORT                      integer, 1–65535
    DATABASE_URL              postgres://… connection string
    REDIS_URL                 redis://… connection string
    JWT_ACCESS_SECRET         min 32 chars, no placeholder values
    JWT_REFRESH_SECRET        min 32 chars, must differ from access secret
    JWT_ACCESS_TTL            duration string, default "15m"
    JWT_REFRESH_TTL           duration string, default "7d"
    BCRYPT_ROUNDS             integer, 10–14, default 12
    CORS_ORIGINS              comma-separated allowlist; "*" is rejected outside dev
    RATE_LIMIT_WINDOW_MS      integer, default 60000
    RATE_LIMIT_MAX            integer, default 5
    EXCHANGE_PROVIDER         one of: mock | live   (mock is used in tests + CI)
    EXCHANGE_API_KEY          required only when EXCHANGE_PROVIDER=live

================================================================================
SECTION 4. STARTUP & SHUTDOWN LIFECYCLE
================================================================================

  1. Load env (.env → Zod parse). On failure: print errors, exit 1.
  2. Construct PrismaClient singleton. Run prisma.$connect().
  3. Construct Redis client. Await ready event.
  4. Mount Express middleware: helmet, cors(allowlist), json parser, request-id,
     pino logger, route table, error handler.
  5. Bind HTTP server.
  6. On SIGTERM / SIGINT: stop accepting new connections, flush in-flight requests
     (10s grace), call prisma.$disconnect() and redis.quit(), exit 0.

================================================================================
SECTION 5. CROSS-CUTTING CONCERNS
================================================================================

  - Logging.  pino with request-id correlation. One log line per request including
    method, path, status, duration, userId (if authenticated).
  - Errors.   Single global error handler. Custom AppError class with .statusCode
              and .code fields. Domain errors (e.g., POOL_FULL, ALLERGEN_MISMATCH)
              map to standardized JSON responses defined in openapi.yaml.
  - Security. helmet defaults, CORS allowlist, rate limit on auth, bcrypt, JWT
              with separate access/refresh secrets, refresh-token denylist in Redis.
  - Audit.    Every state-changing financial action writes one row to AuditLog
              inside the same $transaction as the business write. Audit cannot
              succeed if business write fails, and vice versa.
