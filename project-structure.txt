================================================================================
SECTION 2. ARCHITECTURE EXPLANATION
================================================================================

WHY THIS LAYOUT (vs. flat or feature-first):

  1. Layered separation matches the assignment rubric.
     The grader reads:  "atomic contribution transaction" → opens
     services/contribution.service.js. "Recursive family tree" →
     services/familyTree.service.js. Mapping is 1:1.

  2. Repositories are the only place importing prisma.
     Services that need a transaction explicitly accept a `tx` parameter and
     pass it to repository functions. This makes every transaction boundary
     auditable from a single line of code.

  3. Controllers stay tiny.
     Each controller method:  ① call validate middleware (already mounted via
     router), ② call the service with req.body / req.user, ③ res.status(N).json(...).
     No `if/else` business logic in controllers.

  4. Schemas (Zod) live next to controllers — not buried inside them — so the
     same schemas can be reused in tests.

  5. tests/integration/* mirror the assignment's required-test list:
        - auth.test.js          → covers "Auth Integration Tests"
        - rbac.test.js          → covers "403 for wrong role"
        - contribution.test.js  → covers "overselling is impossible"
        - familyTree.test.js    → covers recursive correctness

  6. CI (.github/workflows/ci.yml) is committed at repo root so the assignment's
     "failing test must make build red" requirement is verifiable in one click
     on the GitHub Actions UI.

WHAT IS DELIBERATELY NOT INCLUDED IN THIS SPRINT (out of 20% scope):

  - Vendor / Courier / Delivery models — domain exists in feature spec but is
    NOT a graded deliverable for this milestone. Will be added in a later sprint.
  - Real exchange-rate provider integration — replaced by `exchange.service.js`
    mock (deterministic rates) so tests are reproducible.
  - Notification subsystem — out of 20% scope.
  - Payment gateway (Kaspi Pay) — contributions are recorded as if escrowed;
    no real money movement. This is explicit in the assignment ("first automated
    payout calculation" not "payment integration").
